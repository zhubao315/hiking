## 一、当前项目审计结果

### 项目源码审计

- 项目是 running_page（yihong0618）模板 fork，Vite + React + TS + Tailwind，构建入口 `vite build`，`PATH_PREFIX=/hiking` 由 CI 注入；`RunMap` / `RunTable` / `TerrainCard` / `JourneyStats` 沿用模板结构。
- **审计起点：hiking 站根本不存在 dashboard 层。** `src/pages/index.tsx` 是模板原始的自由堆叠（`SiteHero` → `YearsStat` → `SVGStat` → `LocationStat` → `JourneyStats` → `RunMap` + `RunTable` → `TerrainCard`），无编号、无双语标题规则、无统一统计口径文件，日历模块不存在。
- 与 running / cycling 两站相比，hiking 缺的是「同一套设计语言」：六个编号模块、英文 kicker 在上中文标题在下、日历收尾、`run_id` 全链路联动。
- 统计逻辑原本散落在组件内部，`JourneyStats` 直接吃跑步逻辑（马拉松场次、配速 `formatPace`），对徒步站会产出错误文案。
- 仓库工作区在 `main` 上干净（`afc4a52`），`src/static/activities.json` 与 `public/scenes/` 均为历史真实数据。

### 首页重复信息和不合理布局（旧版问题清单）

1. 同一组总里程 / 总次数被 `SiteHero`、`YearsStat`、`SVGStat`、`LocationStat` 重复展示 3–4 次。
2. 「最高海拔」与「累计爬升」在视觉上被混为一谈，没有任何覆盖率标注。
3. 跑步专属指标（配速 /km、马拉松、半马）渗入徒步页面。
4. 模块无编号、无双语标题，日历缺失，桌面与移动端排版顺序不一致。
5. 年份热力图（`YearsStat`）与日历职责重叠，但没有单日下钻。
6. 表格无排序、无 `run_id` 联动、`Climb` 列缺失，点击行与地图无关联。

### 统计口径声明（站点内可见）

- 展示数据一律来自 `src/static/activities.json`，统计单源 **`src/utils/hikingStats.ts`**，组件不再各自计算。
- **移动时间**：所有时长只用 `moving_time`（源数据本就没有可用 `elapsed_time`）。
- **累计爬升算法（显式、单一实现 `climbOf`）**：优先取 `climb_terrain`，缺失时回退 `elevation_gain`；随后做**合理性过滤**，不合理的值视为 `null` 而非 0：
  - 有 `altitude_max` 时，`gain ≤ 2.5 × altitude_max`，否则判为 GPS 噪声剔除；
  - 无 `altitude_max` 时，`gain ≤ 100 m/km × 里程`，否则剔除。
  - 原始数据不修改、不删除，只在统计层拒收，因此被剔除的记录仍在表格、地图、日历中可见。
- **累计爬升 ≠ 最高到达海拔**：前者是 `Σ climbOf(run)`，后者是 `MAX(altitude_max)`，两个独立指标、两张独立卡片，各自标注覆盖率。
- **覆盖率必须同屏**：任何爬升 / 海拔数字旁边都带 `覆盖 N / M 次（x%）`，缺数据的年份在趋势图里画 `–` 无数据点，绝不画 0。
- **地理**：只用 `location_country` 解析出的结构化省 / 市，**从未根据坐标反推地名**；覆盖 75 / 344（21.8%），页面直接写明覆盖率。
- **速度 / 配速**：徒步站不展示，`RunTable` 无 Pace 列。

## 五、新增的交互方式

1. **scope 初值同步计算**：默认年份取 `availableYears(runs)` 的最新真实年份（2026），**不用 `new Date().getFullYear()`**，不会出现「当前年无数据但被选中」。
2. 年份柱 / 年份胶囊 / 日历翻年 → 统一改 scope，地图、表格、指标、趋势读出同步。
3. 快捷筛选（省 / 季节 / 时段 / 里程碑）→ `QUICK_PREDICATE` 过滤，标题处显示 `quickLabel` 并给「清除筛选」。
4. Journey 纪录点击 → `focusRun(runId)`：从活动自身读出年 / 月 / 日并设 `selectedRunId`，随后滚到地图（一次点击即定位）。
5. 表格行 / 日历天格 → `selectRun` 开关式选中，地图高亮 + 3D 地形联动。
6. 年份胶囊支持**键盘操作**：`role="button"` + `tabIndex=0` + `aria-pressed` + Enter/Space（实测 2013 + Enter → scope「2013 年」，Total + Space → 「全部历史」）。

## 八、GPS 轨迹异常修复（2026-11-02 追加）

### 8.1 现象与诊断

用户指出 2014 年若干徒步的轨迹线「明显不对」。把每条 `summary_polyline` 解码后按大圆距离累加，与设备记录的 `distance` 对比，**244 条轨迹**的结果是：

| 指标 | 值 |
|------|-----|
| 解析长度 / 记录长度 | 中位 **0.994**（多数轨迹准确）· 最小 **0.415** · 最大 **2.571** |
| 显著偏长者 | 解析长度 > 记录长度 × 1.2 的共 **9 条** |

偏长不是误差，而是**几何本身是错的**：轨迹里出现两枚相邻定位点相距数公里，中间没有采样点，连线把这段空白画成了一条跨越山野的直线。两类成因：

1. **定位点漂移（teleport）**——单点跳到远处又跳回，直线横穿地图，把总长拉长到 2 倍以上；
2. **采样中断（gap）**——一段真实行走完全没有采样点，首尾被直线连接，总长基本不变（比值 ≈ 1.00），但**画出来的是没走过的路**。

比值接近 1.00 的第二类无法靠「长度是否离谱」发现，只能靠**跳步间距是否超过该轨迹自身的采样间距**来识别。另有少量高频 GPS 抖动（相邻点来回 ±5 m），属实测噪声，本次不动。

### 8.2 处理策略（只改绘制，不改数据）

`src/utils/utils.ts` 内新增纯函数 `splitTrack` / `trackPartsForRun`，在**渲染时**清洗几何：

1. **断开**：任一相邻点间距 > `max(300 m, 12 × 该轨迹自身采样间距的中位数)` → 在此断开。断开的区间是**未知路段**，不连直线，直接不画。
2. **去尘**：断开后点数 < 3 或长度 < 150 m 的碎片丢弃（单点漂移留下的噪点）；若整条轨迹只剩尘（全部碎片都太小），保留最长的一段，保证地图上不是空的。
3. **输出**：存活片段 > 1 时输出 `MultiLineString`，否则 `LineString`；结果按 `run_id` 缓存（`Map<number, Coordinate[][]>`），scope 切换不重复解码。

**三条硬边界**：

- `src/static/activities.json` **一个字节都没改**，`summary_polyline` 原样保留；
- 页面上的任何数字（里程 / 时长 / 爬升 / 海拔 / 次数 / 日历热力）**全部未变**——清洗只作用于喂给 MapLibre 的 GeoJSON；
- 无烘焙场景时 3D 地形与海拔剖面走 `public/scenes/`，与 `summary_polyline` 无关，因此**未受影响**。

地图卡片底部新增一行说明，避免用户把断口误读成加载失败：

> 轨迹按记录原样绘制；信号中断处断开显示，不做直线连接。

### 8.3 阈值为什么是 `max(300 m, 12 × 中位间距)`

- **300 m 地板**：普通徒步相邻定位点间距在 10–60 m 量级，300 m 已远超任何正常步进，不会误伤盘山小路；
- **12 × 中位间距**：适配不同设备的采样频率（2022 年后的记录点数可达 8000+，点距更密；2013 年的老记录点距更疏）。用中位数而非均值，避免被跳步本身污染；
- **稳健性**：把参数换成 250 m / 400 m / 500 m 或 `8 × p90`，受影响记录数在 **25–35 条**之间波动（本策略 **32 条**），说明结论对阈值不敏感；
- **上限**：单条轨迹最多断开 5 段，没有出现「碎成渣」的情况。

### 8.7 已知边界

1. 断开处是**信息损失**（真实走过的路没采样），页面用说明文字交代，不试图插值补线；
2. 高频抖动（相邻点 ±5 m 反复横跳）不在清洗范围，属真实噪声，保留原样；
3. 该规则作用于**所有年份**，但历史上只有 2013–2015 与 2022–2023 存在跳步，2024 年之后记录采样完整，无变化；
4. 清洗后绘制长度会小于记录里程的场景（如 2014-03-29）是**如实差异**，不代表数据错误；
5. 断开后仍可能有与主段相距较远的独立片段（如 2014-03-08 东侧 513 点那段）。它满足「≥ 3 点且 ≥ 150 m」门槛，且其里程**计入记录里程**（该条清洗后 12,593 m 对记录 12,639 m，比值 0.996），删掉反而会让图形与里程对不上，因此按记录原样独立绘制；视觉上的分离就是记录里真实存在的空白。

## 十三、84 个 run_id 已被 float64 改写

接上集成闸门时暴露的是一个真实缺陷，不是外观问题：**84 条已发布的 `run_id` 在 `run_page/data.db` 里不存在**。DB 存 `7000000000006376250`，JSON 存 `7000000000006376000`——同一个 IEEE double 的最短往返十进制；`9223370529588379807` 变成 `9223370529588380000`。凡大于 2^53（9,007,199,254,740,992）的 id 经过 double 就丢掉低位，而本仓库的 JSON 会被 Node 脚本改写，id 于是漂离了手表报出的原值。

`run_id` 是连接键：JSON ↔ DB、hiking ↔ running 侧去重清单、记录 ↔ 烘焙的 3D 场景。当前实测的影响面：

- 84 个漂移 id 中，**78 个**既有 `src/static/scenes.json` 条目、又有 `public/scenes/<id>.scene` 文件，两者用的都是**漂移后的**十进制；没有任何一个场景用真实 id 命名；
- 上一节 169 条派生地点里 **23 条**因此写不进 DB（resolver 按 JSON 里的 id 去 UPDATE，DB 没有这一行）；
- running 清单里的 15 个 `hiking_run_id` 全部小于 2^53，未受影响。

### 13.1 已修复（2026-11-06）

`run_page/fix_run_id_precision_rh.py` 只在没有歧义时恢复精确 id：恰好一个 DB id 落在同一个 double 上，且名称、起始时间、里程三项都一致。执行前判定 **84 可修 / 0 歧义 / 0 拒绝**，执行后重新判定 **0 可修**，JSON 的改动是**恰好 84 行 `run_id`、其余字节不变**（`git diff --stat` = 84 insertions / 84 deletions）。此后 `check_data_integrity_rh.py` 以严格模式通过（`--warn-only` 已从本站工作流摘除），DB↔JSON 的记录集合两侧都无缺席；顺带把 169 条派生地点全部镜像进 DB——resolver 按 id UPDATE，id 一正，先前落空的 23 行全部命中（`database run_page/data.db: 169 row(s) updated, 0 run_id(s) absent`）。

### 13.2 场景文件名与 `scenes.json` 的键**故意不改**

计划里原本要连 `scenes.json` 的键和 78 个 `public/scenes/<id>.scene` 一起改名，实测证明改了才会坏：

- 浏览器拿到的是 JS number，`TerrainCard` 用 `String(run.run_id)` 拼出请求路径——**一个 19 位 id 经 `Number → String` 必然回到漂移后的十进制**，所以文件名必须是漂移形式；`src/vert/scenes.ts` 的 `sceneHashOf` 也正是先用字符串、再用 `byNumber` 数值兜底，才让 232 个键在修复后仍全部命中；
- CI 里的烘焙与回填步骤（`scripts/bake-scenes.mjs`、`scripts/backfill-scene-records.mjs`）都是 Node 读同一份 JSON 再写回，文件名永远由 `String(double)` 生成——即使手工改名，下一次烘焙又会生成漂移名的新文件；
- 因此改名会当场断掉 78 条地形链接，而收益只有文件名好看。核对结果：232 条有场景的记录，hash 命中 232/232，`<String(run_id)>.scene` 与 `.scene.json` 成对存在 232/232。

真正需要精确 id 的是**记录本身与 DB 的连接**（手表报出的值、跨库清单、parquet、CSV 都按整数比对），这一层已经修复。

### 13.3 复发防护

漂移的来源是那两步 Node 改写，所以工作流在 `Backfill terrain records and sync into DB` 之后、parquet／README／地点反查／集成检查之前新增 `Restore run_ids rounded away by Node`（`fix_run_id_precision_rh.py --execute`）：每天从 DB 权威值恢复，只改无歧义且三项一致的 id，其余原样报告；紧接的严格集成检查若发现任何残留往返，直接拒绝提交。
